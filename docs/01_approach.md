# 1. Задача и подход

## Три вопроса, на которые система должна отвечать каждый день

| Вопрос собственника | Во что он превращается в данных | Где отвечаем |
|---|---|---|
| Сколько на самом деле зарабатывает каждый артикул? | Вклад в прибыль SKU × месяц: выручка − удержания Ozon **после баллов** − реклама − себестоимость − брак и утраты − фулфилмент − налоги | `mart_sku_month`, блок «Сколько зарабатывает» |
| Где Ozon удерживает лишнее? | Сверки: остатки по движениям, приёмка поставок, отчёт о реализации vs API, реклама vs финансы, утраты vs возмещения, новые статьи начислений | `mart_stock_losses`, `mart_supply_acceptance`, `mart_recon_*`, `mart_dq` |
| Какую модель закупать, а какую выводить? | Прогноз спроса с поправкой на OOS, точка заказа по модели, затоваривание, ABC по прибыли, сценарии тарифов | `mart_purchase_plan`, `mart_stock_plan`, `mart_abc_xyz`, `mart_scenarios` |

## Принципы

1. **Деньги — из финансовых начислений, разрезы — из операций.** Итог по деньгам берём из начислений
   Ozon (`total_amount` — источник истины), а SKU, кластер и рекламную кампанию — из заказов,
   остатков и Performance API. Так цифра на дашборде сходится с кабинетом и отчётом о реализации.
2. **Две картины, и обе честные.** «Сходимая» — по отправлению ровно то, что начислил Ozon.
   «Управленческая» — плюс распределённые общие расходы кабинета (реклама, штрафы, хранение)
   по явным правилам. Правила распределения записаны в SQL, а не в голове аналитика.
3. **Номинальный тариф — не расход.** В 2026 году Ozon считает вознаграждение от цены продавца,
   а на разницу между ценой продавца и ценой для покупателя начисляет баллы, которыми гасит
   до 99% услуг. Пока баллы не «пришиты» к артикулу, юнит-экономика показывает чепуху:
   по отправлению — минус, в конце месяца — большой непонятный плюс. Подробно — в `03_unit_economics.md`.
4. **Закупка — по модели, поставки — по карточке.** Физически один и тот же товар может жить
   в нескольких карточках. Решение «сколько купить» принимается по модели, «сколько и куда
   отгрузить» — по карточке и кластеру.
5. **Мониторинг свежести, а не «скрипт отработал».** Для каждого источника — дата последних
   данных и полнота. Тихое отключение метода API ловится в первый же день.
6. **Каждое число объяснимо.** Любая цифра дашборда раскрывается до строк начислений и отправлений.

## Что поставляется

* Пайплайн «API → raw → staging → marts» (Python + SQL, DuckDB для прототипа).
* Единый справочник SKU/моделей/себестоимости и маппинг статей начислений в P&L (CSV в `data/reference`,
  в проде — Google Sheets с правами для финдиректора).
* Витрины для дашборда и регулярных решений, тесты на сверки.
* Прототип дашборда (`dashboard/index.html`), который в проде переносится в DataLens.
* Плановый калькулятор: цена, акция, сценарии изменения тарифов — откалиброван на факте месяца.

## Чего здесь нет намеренно

* Реальных данных компании: всё, что в репозитории, — синтетика. Механика и схемы рассчитаны
  на то, чтобы в первую неделю подключить боевой кабинет и откалибровать допущения.
* Сложных ML-моделей спроса: на коротких рядах маркетплейса прозрачный метод Хольта с поправкой
  на OOS даёт лучшее соотношение точности и объяснимости. Усложнять — когда появится история за 1,5–2 года
  и метрика точности прогноза, которую есть с чем сравнить.
